# Scope: Core UI scene production

- The current Core has Logical Tree, Control/Layout state, `SceneSnapshot`, and frame submission/completion contracts, but the production path from a Window/Visual tree to a `SceneSnapshot` is not implemented; current scenes are constructed directly in tests.
- `UNIT-CORE-076` implements a pure LayoutEngine kernel with DesiredSize, FinalBounds, and immutable LayoutSnapshot. It accepts an immutable node snapshot and injected intrinsic measurement provider; it is not wired to the live Control tree or Window client-area input. The next unit must connect those inputs before scene production.
- `UNIT-CORE-077` makes Window peer open return a generation-scoped logical client area and routes later updates through the Runtime UI dispatcher. Invalid dimensions are rejected; stale/closed generations are ignored; accepted changes dirty the Window's Visual subtree. Linux direct-KMS currently reports selected mode dimensions as the logical area; dynamic hardware resize and physical scale behavior remain unverified.
- The current public C ABI exposes StackPanel orientation/child alignment and layout dirty inspection, but no public size constraints, root client-size delivery, or bounds query. Do not invent an ABI surface or intrinsic Text sizing rule during implementation; review DD and UT contracts first.
- A reviewed Layout proposal can keep client-area delivery and immutable layout snapshots inside the Rust Core/Platform SPI; it does not need public bounds or measurement callback APIs. Text-family measurement must use a TextService metrics boundary; a fake provider can verify the generic Layout kernel without claiming Text rendering is implemented.
- Platform DD explicitly leaves Visual-tree traversal and scene construction to a later unit. Keep layout/hit-test bounds and renderer geometry on one revision, and preserve Core ownership of immutable snapshots.
- The Linux GLES backend currently renders Clip/FillRect and rejects GlyphRun. A Text UI path needs an explicit TextService/glyph data/render dependency; do not silently drop text or mark unsupported operations presented.
- Keep hardware DRM/KMS confirmation separate from Core scene construction; Docker llvmpipe tests establish only software rendering for the exercised pixels.
- After `UNIT-CORE-078`, the live Control tree does produce a `LayoutSnapshot`; this closes the 076/077 input-integration gap, but no `VisualNode` traversal/Control-to-DrawOp producer exists. Layout bounds are parent-space; absolute scene transform, ancestor-client-clip intersection, draw order, and Visual snapshots remain to be designed.
- `SceneSnapshot` carries `DeviceScale` and background RGB, but no Runtime/Window-owned source was identified for either. Keep the prior user decisions (“Core supplies Scale”, “pass background color”) and define the ownership/update contract instead of choosing renderer defaults.
- Requirement RQ-09-072 requires single-paragraph text display and client clipping, not soft-wrap/ellipsis/selection-copy. Button label and Accessibility name are separate. Text color/appearance and font/profile asset resolution must be explicit; Style/Theme/Template are later scope and do not authorize implementation-only placeholder defaults.
- Relevant platform requirements include Core source-of-truth/replaceable renderers (RQ-11-008/009), failure not reported as success (RQ-11-020), backend/fallback identification (RQ-11-022), and font/profile contracts (RQ-11-023/024). Candidate DirectWrite/Fontconfig/HarfBuzz/FreeType/Noto references in DD are not installed dependencies or a finalized deployment profile.
- `window_submit_frame` consumes a caller-created `SceneSnapshot`; dirty-to-Layout-to-Scene-to-submit scheduling and a Control-to-Scene producer test/unit mapping are absent. Include both in the DD and UI unit-test proposal before implementation.
- Keep the existing downstream `RenderBackend` seam distinct from the missing Control-to-View connector. The user wants backend-neutral View/Visual contracts so multiple renderer implementations (e.g. WinAPI/OpenGL/Vulkan on Windows) can be selected; OS Window/native-surface ownership and rendering API/backend may be separate axes. Define composition, selection, capabilities and failure reporting in reviewed design rather than baking a renderer into Controls.
- The current proposal treats existing immutable `SceneSnapshot` as the single backend-neutral View snapshot produced by `ControlViewConnector`, avoiding two competing visual/scene snapshots. Platform selection composes an OS `WindowPeer`/native surface with an independently selected compatible `RenderBackend`; the combination/fallback policy remains review-bound.
- `UNIT-CORE-080` implements an ephemeral VisualNodeSnapshot + same-revision LayoutSnapshot to SceneSnapshot geometry/clip projection. The approved DD says Layout FinalBounds are parent-relative, but the existing LayoutEngine had accumulated ancestor origins into child FinalBounds. Keep FinalBounds parent-relative in LayoutEngine and compose absolute DIP coordinates in ControlViewConnector; do not compensate twice. Scene production is not yet connected to the live Control tree, text/font realization, dirty-to-frame scheduling, or a Linux physical renderer.
- `UNIT-CORE-081` adds a revision-stamped non-owning ControlTreeSnapshot and requires an exact identity-to-VisualNodeDescriptor mapping before producing a SceneSnapshot. Tests use fake descriptors only; this must not be treated as a production appearance, font, or live Runtime tree capture implementation. Keep unresolved control clip policy and Text/Button appearance explicit.
- `UNIT-CORE-082` captures the attached Core Logical Tree only on the UI thread and only while the Window is open, the exact published LayoutSnapshot is current/clean, and its tree revision matches. Layout dirtiness from property/tree changes must reject capture until a new complete LayoutSnapshot is published. The result is non-owning and includes no Visual descriptors.
- `UNIT-CORE-080`/`081`/`082` are pushed on `impl-rust/core-scene-rendering` through `1747f33`. The next identified gap is DeviceScale transport: `PlatformWindowPeer::open` currently returns only `WindowClientArea`, `WindowLifecycle` stores no scale, and production Scene input cannot use the Core-owned environment scale. Linux KMS currently reports mode pixel extent as the same numeric DIP extent; do not infer physical DPI or silently bless scale 1.0 without an approved profile contract. See `.docs/20_todo/core-device-scale-transport.md` for the review proposal.
- `UNIT-CORE-083` adds `WindowOpenInfo { client_area, device_scale }` to the private peer SPI, stores scale with the Window generation, and lets Core runtime scene production read it. Linux direct-KMS explicitly supplies `(1,1)` because its current profile reports mode pixel extent as numeric DIP extent; this does not imply physical DPI or HiDPI validation. The Core fake-peer test confirms anisotropic scale reaches `ControlViewConnector` without modifying DIP client area.
- Next open scope is Linux text rendering profile selection. RQ-09-072 requires basic single-paragraph Text display, but the approved design still lists font stack/assets and appearance details as candidates; GlyphRun has no color/profile asset binding and Linux GLES rejects it. Review `.docs/20_todo/linux-text-rendering-profile.md` before adding dependencies or production visual descriptors. Do not infer color/font defaults from implementation convenience.
- RQ-09-075, Platform DD 1.9, UI Controls DD 1.4, UI UT 1.2, and implementation plan 0.3 were approved on 2026-10-31. For unspecified fonts, Core sends a neutral PlatformDefault request; Platform TextService resolves the OS/profile default and returns immutable metrics/glyph runs with each resolved face identity. Core reuses the same resolved snapshot for Measure and Scene. Linux DRM/KMS is headless, so Fontconfig defaults are not desktop GNOME/KDE font preferences. Plan 0.3 selected Fontconfig `sans-serif`, `FC_LANG=ja-jp` in Docker, `FcFontSort(NoTrim)`, `fontconfig 0.11`, `harfbuzz 0.8`, `freetype-rs 0.38`, Debian 12 packages, and a Latin/Japanese/mixed corpus.
- Implementation plan 0.3 was approved on 2026-10-31. UNIT-CORE-084 adds `crates/core-runtime/src/text_service.rs` with Core-neutral `PlatformDefault`, revision-stamped immutable resolved metrics/glyph runs, and per-run resolver/profile/font-face identity. Its fake tests cover profile-specific identity, revision mismatch, digest consistency, and failure without partial result; actual Control/Layout/Scene wiring is UNIT-CORE-085, and Linux realization/rendering remains separate. It was tested and pushed as `b6c64ea`. Keep the service trait internal to Rust Core; do not add C ABI/wrapper surface for this seam.
- UNIT-PLATFORM-003 implements Linux Fontconfig candidate resolution, grapheme fallback assignment, HarfBuzz shaping, FreeType metrics and grayscale glyph-mask cache. `freemvvm-platform-linux::text_service()` exposes the service only as an internal Rust integration seam; `abi_support` is doc-hidden and no C ABI/wrapper API was added. Debian 12 Docker workspace tests, Clippy, Rust 1.85 check, and fmt passed. The C ABI control test skips Linux `Window.open` to keep CI hardware-independent; hardware validation remains separate. UNIT-CORE-085 wires Text control/layout/scene snapshots, and UNIT-PLATFORM-004 renders masks through GLES.
- Ubuntu CI compiling `freetype-sys` requires `libfreetype-dev` plus `pkg-config`; the Linux runner also needs `libharfbuzz-dev`, Fontconfig and `fonts-noto-cjk` for the Japanese corpus. Set `FC_LANG=ja-jp` on the Linux gate to match the approved Docker oracle. Keep runner package preparation in `.github/workflows/bootstrap.yml` aligned with `docker/linux-platform/Dockerfile`.
- UNIT-CORE-085 passes the same immutable resolved Text snapshot from Platform TextService into Layout metrics and Visual GlyphRun production. Publish Layout and its text snapshot map atomically; a failed resolution keeps the previous complete pair. Display-property changes must dirty Layout so the next layout revision re-resolves text. The present production caller/scheduling path is still separate from the tested Core operation; do not claim that hardware frame presentation is complete.
- UNIT-CORE-085 was pushed as `d489ca5`; workspace tests, Clippy, Rust 1.85 check, fmt and both Windows/Ubuntu CI gates passed (Actions run `41204164249`). This verifies Core snapshot handoff, not Linux DRM hardware presentation or UNIT-PLATFORM-004 GLES glyph rendering.
- The first Ubuntu CI after adding `freetype-sys` failed because runner preparation omitted `libfreetype-dev`/`pkg-config`; run `41201554822` confirms `freetype2.pc` was missing. Adding Linux Fontconfig/CJK/FreeType/HarfBuzz packages in bootstrap made run `41202444544` pass both Ubuntu gates. Keep CI runner dependencies synchronized with the Docker profile.
- `UNIT-PLATFORM-004` sends Core-owned opaque-black GlyphRun paint through the existing SceneSnapshot and shares the same LinuxTextService instance from PlatformFactory to GLES renderer. FreeType gray/mono masks are normalized for signed pitch, uploaded to an R8 shelf atlas and cached by font digest, size, DeviceScale, and glyph ID. Atlas UVs must follow OpenGL's low-V first uploaded row; reversing that assumption yields a successful draw with no visible glyph pixels. Debian 12 llvmpipe headless EGL verifies glyph pixels, anisotropic scale, clip, missing identity and GL error failure; this is software-rendering evidence only, not DRM hardware presentation.
- UNIT-CORE-086 adds production descriptor data to the UI-thread captured `ControlTreeNodeSnapshot`: StackPanel/container nodes clip descendants; initial leaf Controls add no chrome, while Text/TextBox/Button contribute only their same-layout-revision resolved GlyphRuns. `ControlViewConnector::build_from_production_control_tree` validates the tree/layout and text/layout revisions before creating one complete SceneSnapshot. Preserve the existing descriptor-map route for focused structural tests. The production test rejects a deliberately stale text snapshot and verifies TextService font identity remains shared with Layout output. UNIT-CORE-086 local gates and Windows/Ubuntu CI passed (run `41209924293`, commit `66fe771`). The only plan gap left is UNIT-CORE-087 dirty-to-frame orchestration; Linux hardware display remains deferred.
