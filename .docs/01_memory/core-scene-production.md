# Scope: Core UI scene production

- The current Core has Logical Tree, Control/Layout state, `SceneSnapshot`, and frame submission/completion contracts, but the production path from a Window/Visual tree to a `SceneSnapshot` is not implemented; current scenes are constructed directly in tests.
- `UNIT-CORE-076` implements a pure LayoutEngine kernel with DesiredSize, FinalBounds, and immutable LayoutSnapshot. It accepts an immutable node snapshot and injected intrinsic measurement provider; it is not wired to the live Control tree or Window client-area input. The next unit must connect those inputs before scene production.
- `UNIT-CORE-077` makes Window peer open return a generation-scoped logical client area and routes later updates through the Runtime UI dispatcher. Invalid dimensions are rejected; stale/closed generations are ignored; accepted changes dirty the Window's Visual subtree. Linux direct-KMS currently reports selected mode dimensions as the logical area; dynamic hardware resize and physical scale behavior remain unverified.
- The current public C ABI exposes StackPanel orientation/child alignment and layout dirty inspection, but no public size constraints, root client-size delivery, or bounds query. Do not invent an ABI surface or intrinsic Text sizing rule during implementation; review DD and UT contracts first.
- A reviewed Layout proposal can keep client-area delivery and immutable layout snapshots inside the Rust Core/Platform SPI; it does not need public bounds or measurement callback APIs. Text-family measurement must use a TextService metrics boundary; a fake provider can verify the generic Layout kernel without claiming Text rendering is implemented.
- Platform DD explicitly leaves Visual-tree traversal and scene construction to a later unit. Keep layout/hit-test bounds and renderer geometry on one revision, and preserve Core ownership of immutable snapshots.
- The Linux GLES backend currently renders Clip/FillRect and rejects GlyphRun. A Text UI path needs an explicit TextService/glyph data/render dependency; do not silently drop text or mark unsupported operations presented.
- Keep hardware DRM/KMS confirmation separate from Core scene construction; Docker llvmpipe tests establish only software rendering for the exercised pixels.
- After `UNIT-CORE-078`, the live Control tree does produce a `LayoutSnapshot`; this closes the 076/077 input-integration gap, but no `VisualNode` traversal/Control-to-DrawOp producer exists. Layout bounds are parent-space; absolute scene transform, ancestor-client-clip intersection, draw order, and Visual snapshots remain to be designed.
- `SceneSnapshot` carries `DeviceScale` and background RGB, but no Runtime/Window-owned source was identified for either. Keep the prior user decisions (“Core supplies Scale”, “pass background color”) and define the ownership/update contract instead of choosing renderer defaults.
- Requirement RQ-09-072 requires single-paragraph text display and client clipping, not soft-wrap/ellipsis/selection-copy. Button label and Accessibility name are separate. Text color/appearance and font/profile asset resolution must be explicit; Style/Theme/Template are later scope and do not authorize implementation-only placeholder defaults.
- Relevant platform requirements include Core source-of-truth/replaceable renderers (RQ-11-008/009), failure not reported as success (RQ-11-020), backend/fallback identification (RQ-11-022), and font/profile contracts (RQ-11-023/024). Candidate DirectWrite/Fontconfig/HarfBuzz/FreeType/Noto references in DD are not installed dependencies or a finalized deployment profile.
- `window_submit_frame` consumes a caller-created `SceneSnapshot`; dirty-to-Layout-to-Scene-to-submit scheduling and a Control-to-Scene producer test/unit mapping are absent. Include both in the DD and UI unit-test proposal before implementation.
- Keep the existing downstream `RenderBackend` seam distinct from the missing Control-to-View connector. The user wants backend-neutral View/Visual contracts so multiple renderer implementations (e.g. WinAPI/OpenGL/Vulkan on Windows) can be selected; OS Window/native-surface ownership and rendering API/backend may be separate axes. Define composition, selection, capabilities and failure reporting in reviewed design rather than baking a renderer into Controls.
