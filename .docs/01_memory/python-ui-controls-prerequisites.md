# [Python wrapper / UI Controls prerequisites]

- Python wrapper surfaceを実装計画に載せる前に、DDの公開API一覧・source class一覧・unit inventoryを照合する。Python Runtime/Property完了はBinding/Commandの存在を意味しない。
- 0.0.1 release計画はPythonを含む4言語すべてにProperty/Binding/Command/UI Control vertical sampleを要求する。Python側にはRuntime/Propertyまであり、Binding/AsyncCommand/Control/Window facadeは未実装。
- `impl-python/runtime-wrapper`は`impl-rust/core-ui-controls-c-abi`を祖先に持つ。C# UI Controlsは`impl-csharp/ui-controls-wrapper`で別途完了済みだが、Python branchへmergeせず、要求・共通C ABI・Python DDをPython実装の根拠にする。
- UI Controls plan v0.1がBinding/Commandを「既存」と誤認したため、実装開始前にv0.2でBinding/AsyncCommandを先行依存unitとして追加した。計画scopeの承認はDD/test design/implementation approvalと別に管理する。
- Binding wrapperは承認済みRQ-07と共通C ABIを正本とする。ABI上OneTimeは成功時Binding handle 0、OneWay/TwoWayは所有handleを返し、handle releaseだけでは接続を解除しない（明示cancelまたはRuntime shutdown）。Python DD v1.7とwrapper test design v0.9は2026-10-26に文書全体が承認済み。`UNIT-WRAP-PY-BINDING-001`はfake ABI 29件・実C ABI consumer・Windows local `check`/`minimum`・Windows/Linux CI run 40212415054が成功しcomplete。Command以降の実装は別unit・別承認。
- Python AsyncCommandは承認済みC ABIの`runtime_post`でterminal completionをUIへ戻せる。Command専用progress ABIはなく、既存Command DDは通常Property更新をpost経由で行う形を許す。Python DD v1.8は`CommandOperation.post(callback, *args)`で最小dispatchを提供し、専用progress object/executor/asyncio統合は増やさない。計画・DD v1.8・test design v1.0は2026-10-26に文書単位で承認され、`UNIT-WRAP-PY-COMMAND-001`はlocal check/minimumとWindows/Linux CI成功後にcomplete。
- Python AsyncCommand実装では、start callback rootがRuntime owner tokenを独立保持し、C destroy thunkはrootをregistry lock中に破棄せずsafe-point retire queueへ移す。worker operationのterminal post受付後にworkerが`close()`を呼んでも、UI completion callbackが済むまではCommand/Runtime leaseを保持する。C ABI consumerはhost event scope内executeとsuccess/failure/cancel/re-execute/Property postを通して検証する。`UNIT-WRAP-PY-COMMAND-001`はfake API 4件、実C ABI consumer、Windows local check/minimumと実装SHA `aaf1ce68d3cd090c93631bdd065b3678a687d010`のWindows/Linux CI run 40214188291成功後にcomplete。
- 初期UI C ABIにはControl生成・Property・Tree・StackPanel設定・Focus要求がある一方、Window openは現状`UI_UNSUPPORTED`で、Widget concrete kind queryもない。Python Controls facadeではcontent/child getterを共通Widget viewに留め、推測castしない。Window peer/close-request、成功するFocus統合経路、TextBox editing/IME facadeは別段階にする。
- Python wrapper DD v1.10とwrapper test design v1.1のControls/Tree/Focus範囲は2026-10-26にそれぞれ全文承認された。`UNIT-WRAP-PY-CONTROLS-001`は登録・実装開始承認済みでlocal gates成功、CI確認待ち。
- Python Controls着手時にC ABI mappingの差を検出: `container_*`は複数子StackPanel向け、Windowは専用single-content API。Python facadeではWindowをWidget、StackPanelをContainerとするDD v1.10を2026-10-26に承認。CoreのWindow Container分類・Tree ownership意味は変更しない。
- Python Controls実ABIでBinding通知の更新をconsumer確認する場合、Runtimeへhost UI loop bridgeを登録し、source変更をhost event scope内で行う必要がある。Buttonが保持するCommand associationはButton owner解放後にCommandをcloseすると`BUSY`を避けられる。
- `UNIT-WRAP-PY-CONTROLS-001`はDD v1.10・test design v1.1承認後に登録し、利用者の実装開始承認後に実装。14 fake ABI tests、OneWay/TwoWay BindingとButton Command associationを含む実C ABI consumer、Windows local check/minimum、最終SHA `84e994715c5fbe189e4fd3d68f351d684516440a`のWindows/Linux CI run 40216602669成功後にcomplete。
- Python Window peer/close-request unitの計画0.1、DD v2.0、wrapper test design v1.2は2026-10-26に利用者が文書単位で承認。既存`Window.close()`はowned Control token releaseなのでpeer終了は`close_peer()`に分離した。host `window_open`は`UI_UNSUPPORTED`であり、公開C ABIにclose intent triggerがないため、consumerはsubscription登録/cancelとopen status伝達まで、callback判断/lifecycleはfake ABIおよび既存Core/C ABI試験へ分ける。`UNIT-WRAP-PY-WINDOW-001`はplanned登録、実装開始は未承認。
