# MVVM UIライブラリ Runtime通知上限・診断の上位判断案

- 状態: BD-03承認済み（2026-09-26）
- 対応: 要求仕様第12節「binding循環の扱い」の動的反復、BD-02で残した通知配信回の上限・診断
- 根拠: 承認済みR4・P2～P4・B2・D1～D4・BD-02。DD-00は未承認

## BD-03 承認された判断

**Runtimeが行う通知配信に、UIを占有し続けないための有限の作業枠を設ける。枠を使い切っても未配信の通知を捨てず、完了済みの配信回の境界でUIイベントループへ制御を返し、後続のUI処理区間で配信を再開する。** 単に枠を超えたことだけでは循環とみなさない。反復が収束しないことをRuntimeが判定した場合は、原因となった通知連鎖の再配信を停止し、診断可能な状態を残す。無関係な通知は継続する。

| 項目 | 提案する上位契約 |
|---|---|
| 作業枠 | 一度に連続して実行するRuntime管理下のBinding伝播・通知配信を有限にする。具体的な回数・時間・計測点は詳細設計で決める。 |
| 制御を返す境界 | Binding伝播や個々の配信回の途中では中断せず、完了した配信回の後で譲る。処理済み部分の順序と、既に確定したProperty値を保持する。未配信部分は次回に持ち越す。 |
| 大量の有限更新 | 作業枠到達を障害とは扱わず、保留中の配信を進める。保留があること、および進行状況を診断できるようにする。 |
| 非収束する反復 | 作業枠到達を繰り返すだけでは確定診断とせず、循環状態など非収束と判断する根拠を要する。判定した通知連鎖の自動再配信を止め、原因・影響範囲・停止状態を診断として公開する。別の連鎖を巻き添えにしない。 |
| コンパイル時の静的警告 | イベントcallbackが、そのイベント元と同じControlのPropertyにアクセスすることを静的に検出できる言語では警告する。診断では読み取りと書き込みを区別し、書き込み、とくに同じPropertyへの書き戻しを強い警告対象とする。これは循環の可能性を示す警告であり、実行時の無限反復を断定しない。 |
| Python | Pythonには通常のコンパイル時警告を要求しない。静的解析ツールを使う場合の検出は任意とし、Runtime側の保護・診断は他言語と同じ契約にする。 |
| 停止後 | 確定済みの値は巻き戻さない。停止した連鎖の保留通知を黙って破棄・再開しない。復旧条件と明示的な再開／破棄操作の具体APIは詳細設計で定める。 |
| 診断経路 | 長期保留と停止を区別し、アプリがUI thread上で観測できる診断を設ける。診断通知そのものが同じ配信反復を増幅しないようにする。形式・購読方法・蓄積上限は詳細設計へ送る。 |

### P3への反映

承認済みP3の通常規則は、外側のUI処理が戻った後、次の通常UIイベントまたはdispatcher postの前に通知を配信すること。BD-03は、有限作業枠に達した後の未配信通知について例外を設け、次の通常UIイベントやdispatcher postが先に実行され得るものとする。処理済み通知の順序、同一Propertyのまとめ、通知callbackから生じた変更を次の配信回へ送る規則、および同期flushを設けない規則は維持する。次のイベントが観測するのは確定済みのProperty値であり、保留通知の状態を診断できる。

## 選択理由と限界

- 無制限の連続配信は、通知callbackによる反復でUIイベントループを占有する。毎回の配信を単に打ち切る方式は更新を失い、有限だが大きい更新と循環を区別できない。
- 完了した配信回の境界で譲ることで、Runtime自身が途中でBinding伝播を割らずにUIへの応答機会を作る。ただし複数回の配信をまたぐ観測が必要な画面では、途中の状態が次のイベントから見える。原子的な複数Property更新はBD-02のとおり保証しない。
- Runtime管理下の配信に対する制約であり、アプリ側の一つの同期callbackやValidatorが長時間戻らない場合の応答性までは保証しない。非同期Command等で長時間処理をUI threadから外す既存方針を維持する。
- 任意の更新処理が将来収束するかを一般に確実には判定できない。循環を立証できない長期反復には停止を保証せず、作業枠によるUIへの譲りと長期保留の診断を継続する。停止判定の対象と限界を詳細設計で明示する。
- 同一ControlのProperty参照を検出する警告は、直接書かれた参照など解析可能な範囲に限られる。別関数への委譲、reflection、実行時に選ぶControlなどを通じたアクセスは検出できない場合がある。また、読み取りだけのcallbackは通常循環を作らないため、警告は誤検知を含むリスク提示として扱い、エラーにはしない。各言語でどのビルド工程が警告を出すか、解析範囲と例外指定方法は詳細設計で定める。
- 「原因となった連鎖」を判定できるだけの因果関係、保留通知の公正な再開順序、停止後の回復方法、診断の具体形式は詳細設計で詰める。独立した連鎖との切り分けができない実装を許容する意味ではない。

## 承認記録
