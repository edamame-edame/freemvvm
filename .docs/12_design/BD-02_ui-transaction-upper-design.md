# MVVM UIライブラリ UI transactionの上位判断

- 状態: BD-02承認済み（2026-09-26）
- 作成日: 2026-09-26
- 対応: 要求仕様第12節「UI transactionの有無」
- 根拠: 承認済みP2・P3・B2・D3・R4。DD-00は未承認

## BD-02 承認された判断

**初期公開版では、利用者が明示的に開始・commit・rollbackするUI transactionを設けない。** 代わりに既存の「外側のUI処理区間」を、Bindingと通知をまとめる単位として採用する。これはP2・P3・B2・D3を維持する判断であり、新しい一括更新APIや同期flush APIの提案ではない。

| 観点 | 初期版で採る規則 | 承認済みの根拠 |
|---|---|---|
| 値の確定 | 個々のsetterが検証に成功した時点で値を確定し、続くgetterから読める。失敗したsetterはその値を変更しない | P2、V1 |
| 配信とBinding | 外側のUIイベント・投稿callback・UI API処理が戻った後にBindingを伝播し、同一Propertyの通知をまとめる。通知callbackが生んだ変更は次の配信回。有限作業枠に達した場合はBD-03に従って配信回の境界でUIへ譲り、保留通知を後続区間で再開する | P3、B2、D3、R4、BD-03 |
| 失敗と取り消し | 同じ処理内で先に成功した別のsetterは、後続の検証失敗を理由に巻き戻さない。処理全体の自動rollbackは保証しない | P2、V1～V4と整合する提案 |
| 明示API | `begin/commit/rollback`や通知の同期flushは初期版に追加しない | P3の既存の処理区間を用いる提案 |

例えばUIイベントで`A=1`を設定した後、`B`のValidatorが候補を拒否した場合、`A`は1のままで`B`は旧値のままとなる。外側の処理が戻った後、変更された値のBinding伝播と通知が行われる。アプリが二つの値を不可分に変更したい場合は、更新前に両候補を検証してからUI thread上で書き込む設計、または単一の合成Propertyとして状態を表す設計を検討する。ただし、この手順だけで全失敗経路の原子的な複数Property更新が保証されるとは主張しない。

## 判断理由と範囲

- 明示transactionを追加すると、既に承認されたsetter直後のgetter、通知の配信境界、Bindingの初期同期やValidator失敗時の巻戻しの意味が増える。初期縦断シナリオは既存の処理区間と個別setterで成立するため、現時点では追加しない。
- 画面の描画上の更新まとめやModel/DBのtransactionは本判断のUI Property transactionと別の境界。それぞれの要件が出たときに扱う。
- 計算済みProperty・複数フィールドの不可分更新・undo/redo等で必要性が確認されたら、既存の即時確定・遅延通知を破らない拡張か、新しい原子的操作を別の上位判断で設計する。
- 通知配信の有限作業枠、保留、UIイベントループへの譲り方、非収束連鎖の診断・停止はBD-03で別途承認済み。具体的な上限値・検出方法・復旧APIは詳細設計事項であり、本判断の未決項目ではない。

## 承認結果

2026-09-26に承認。初期版は明示的なUI transactionを公開せず、承認済みの外側のUI処理区間でBindingと通知をまとめ、複数setterの自動rollbackは保証しない。通知配信の上限・診断は後続のBD-03で承認済み。
