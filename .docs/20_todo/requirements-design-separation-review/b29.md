## 設計本文の改訂案

build結果にmanifestを対応付け、native bytesのdigestとtarget/profile/ABI/featureをimmutable identityへ束縛する。配布catalogはそのidentityを公開し、consumerはsignatureと適合条件を照合して検証済みstagingへ取り込む。aliasは解決入口だけに使い、解決済みidentity/digestをlockへ記録する。

```mermaid
flowchart LR
    N0["build bytes"]
    N1["digest/manifest"]
    N0 --> N1
    N2["署名"]
    N1 --> N2
    N3["catalog"]
    N2 --> N3
    N4["検証"]
    N3 --> N4
    N5["immutable staging"]
    N4 --> N5
```

## 移管・ID・検証への影響

- 既存ID: BD-29。方式として残る意味は旧IDを維持し、要求へ分ける文だけを仮候補IDに対応付ける。正式RQ IDの発番は[移行案](id-migration.md)による。

- 設計を説明する所有・state・call図と計算例は保持する。対象本文の試験節は、[検証改訂案](test-impact.md)へ対応付けてから移す。失敗時の状態表・cleanup順まで検証扱いで削除しない。
- 上流RQ/ADR/BDへの参照は該当記述に直接置く。後続の着手割当は計画へ移し、DD間のinterface依存参照は実際の定義側へ向けて循環を解く。文書番号の大小だけで依存を判定しない。
