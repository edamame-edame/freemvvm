原文 本文項目1 / L16:

> artifact catalogから取得した公開keyだけを、その場で自動信頼してはならない。 公式publisherのtrust rootは、検証済みwrapper/tool配布物または運用者が明示的にprovisionしたtrust bundleから得る。manifest署名keyは、この既存trust rootまで連なる場合だけ有効とする。

> manifestの署名key identityを固定して検証する。 key identityが未知、失効済み、trust chain不成立、署名不正の場合はfail closedとし、未署名・検証不能の公式artifactをwarning-onlyで利用可能にしない。

## 設計本文の改訂案

consumerの検証器は配布物または運用者provisionのtrust bundleを入力としてkey identityを解決する。artifactと同時に取得した鍵だけで信頼を開始しない。認証済みkeyset更新でrotationを適用し、revocation状態を先に確認して署名検証結果と利用可否を分ける。offlineでも明示bundleから同じpolicyを評価する。

```mermaid
flowchart LR
    N0["独立trust bundle"]
    N1["key/失効照合"]
    N0 --> N1
    N2["signature確認"]
    N1 --> N2
    N3["policy許可/拒否"]
    N2 --> N3
```

## 移管・ID・検証への影響

- 既存ID: BD-31。方式として残る意味は旧IDを維持し、要求へ分ける文だけを仮候補IDに対応付ける。正式RQ IDの発番は[移行案](id-migration.md)による。
- 移管先: 利用者可視条件は上記RQ候補、C/言語APIの具体形はDD内、脅威と防御はSD、試験操作と判定手順はrequirements-test/unit-test、着手順と下流割当はto-do。
- 設計を説明する所有・state・call図と計算例は保持する。対象本文の試験節は、[検証改訂案](test-impact.md)へ対応付けてから移す。失敗時の状態表・cleanup順まで検証扱いで削除しない。
- 上流RQ/ADR/BDへの参照は該当記述に直接置く。後続の着手割当は計画へ移し、DD間のinterface依存参照は実際の定義側へ向けて循環を解く。文書番号の大小だけで依存を判定しない。
