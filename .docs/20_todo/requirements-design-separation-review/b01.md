## 設計本文の改訂案

初期Property値はCoreの型別値領域へ格納し、wrapperの値変換層から固定幅値またはUTF-8を受け取る。数値比較層はkind別の同値判定を行い、setterは検証に成功して差分がある場合だけ値をcommitする。同値時は格納表現を保持し通知を作らない。DECIMALは符号・scale・係数を論理要素として扱い、bit配置はDDのwire表現へ分ける。CollectionModelは値kindに含めず、model handleをControlへ接続する。

```mermaid
flowchart LR
    N0["言語値"]
    N1["明示変換"]
    N0 --> N1
    N2["kind別検証"]
    N1 --> N2
    N3["同値判定"]
    N2 --> N3
    N4["値commit"]
    N3 --> N4
    N5["通知"]
    N4 --> N5
```

## 移管・ID・検証への影響

- 既存ID: BD-01。方式として残る意味は旧IDを維持し、要求へ分ける文だけを仮候補IDに対応付ける。正式RQ IDの発番は[移行案](id-migration.md)による。
- 移管先: 利用者可視条件は上記RQ候補、C/言語APIの具体形はDD内、脅威と防御はSD、試験操作と判定手順はrequirements-test/unit-test、着手順と下流割当はto-do。
- 設計を説明する所有・state・call図と計算例は保持する。対象本文の試験節は、[検証改訂案](test-impact.md)へ対応付けてから移す。失敗時の状態表・cleanup順まで検証扱いで削除しない。
- 上流RQ/ADR/BDへの参照は該当記述に直接置く。後続の着手割当は計画へ移し、DD間のinterface依存参照は実際の定義側へ向けて循環を解く。文書番号の大小だけで依存を判定しない。
