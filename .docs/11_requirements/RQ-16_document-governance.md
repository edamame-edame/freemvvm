# RQ-16: 要求・設計文書の管理と承認

- 文書版: 0.7
- 状態: 承認済み（利用者、2026-10-17）
- 更新日: 2026-10-17
- 入口: [要求仕様索引](reqirements-specification.md)

## 概要

要求、ADR、調査資料、設計の用途と、要求変更および文書間不整合の記録方法を定める。要求の承認は要求仕様書側で完結し、基本設計や詳細設計の承認を要求承認の前提にしない。

本章は提供機能・利用条件・外部から観測できる結果を定める。各IDの対象段階を区別し、将来候補の列挙を採用承認とはしない。

| <a id="rq-16-001"></a>RQ-16-001 | ADRの役割 | ADRはアーキテクチャ上の決定、決定理由、適用範囲、状態を記録する。 | 現行 |
| <a id="rq-16-002"></a>RQ-16-002 | 調査資料の役割 | 調査資料は外部根拠、比較対象、代替案、未決事項を記録する。 | 現行 |
| <a id="rq-16-003"></a>RQ-16-003 | 要求の変更承認 | 要求仕様書を承認済み要求の正本とする。要求変更は要求側で対象範囲と受入条件をレビュー・承認し、BD、API具体化を含むDD、SD、要求test、softwareおよび対応unit-testへの影響を追跡する。要求の承認は要求仕様書側で完結し、基本設計の承認を前提にしない。各文書には承認履歴表と改訂履歴表を設け、承認履歴に日付・対象版またはID・承認者・結論・根拠を、改訂履歴に版・日付・変更内容/理由・作成者・承認履歴との対応を残す。記録は追記し、過去履歴を上書きしない。 要求の変更承認、設計の変更承認、case設計、実装・実行状態を別々に追跡し、旧IDと新しい意味単位の対応を確認できること。 | 現行 |
| <a id="rq-16-004"></a>RQ-16-004 | 要求・ADR・設計の不整合処理 | 要求、ADR、設計に不整合がある場合は、それぞれの承認範囲と差異、影響を記録し、要求変更またはADR/設計変更として明示的に整合する。解決までは適用中のAccepted ADRの制約を維持し、影響する設計・実装を保留する。要求を下流設計に合わせて暗黙に変更しない。Accepted ADRの制約を変える場合は、そのADR変更を別途承認する。 | 現行 |

## 適用境界

承認は要求本文の範囲で完結する。API名・内部データ構造・処理方式の確定を前提にしない。既存ADRによるRust Core・versioned C ABI等の明示的な構成制約は維持する。
